# 食在北車

以台北車站中央大廳為中心的餐廳檢索與 RAG 問答網站。純靜態 HTML、CSS、JavaScript，可直接部署到 GitHub Pages，不需在網頁放 API Key。

目前收錄 **89 筆餐點／料理類型、22 家餐廳、9 種國家／地區風味、47 個來源**。查閱日：2026-11-13；查閱日不是來源更新日。菜單非即時庫存。料理國家指風味分類。

## 使用方式

開啟 `/food-rag/`，輸入「想吃韓式料理，有飯、不吃牛」或使用料理、主食、食材篩選。調整搜尋半徑及距離權重。打字提問預設從全新條件開始，勾選「沿用上一題條件」即可延續上次送出的篩選條件。建議問題按鈕每次使用全新條件。可切換相對位置示意圖、查看來源與收藏餐廳。

詢問「小籠包多少錢」或「小籠包營業時間」時，系統以菜名查詢知識庫，並標明缺少的資訊。回答下方可展開「查看本次檢索依據」→「提示詞」，查看本次的系統指令、問題、條件和檢索資料。檢索摘要模式也提供提示詞預覽。

「口味重」「重口味」「味道濃一點」會依餐點既有的辣味、蒜香標籤與濃郁描述篩選，可搭配料理、主食與距離條件。回答會列出各餐點命中的風味依據。詢問「重口味但不辣」會排除已標註辣味的餐點，實際辣度仍以店家說明為準。

「口味淡」「清淡」「清爽」可找帶有清燉、蒸點、茶香等線索的餐點，實際調味以店家說明為準。「想吃甜的」使用甜點標籤，「酸酸甜甜」對應酸甜與糖醋。若問到未收錄的預算、用油量、鹽分、排隊時間或外帶資訊，系統會提示資料缺口。有菜名或其他可核對條件時，可繼續查找相符的餐點。

每次搜尋只顯示最新一筆問答、引用來源與檢索依據，並將餐廳卡片重設為前 8 家，避免多次搜尋讓頁面持續增長。點「重設」也會清除問答區。頁面最下方提供 RAG 原理、本站檢索與距離加權流程、兩種回答模式及延伸閱讀。

## 真正的 RAG 與預設摘要

預設使用**檢索摘要**：執行真實的知識檢索，再用程式整理資料，不是 LLM 生成。點「檢索摘要模式」→「下載並啟用 AI」後，才會啟用完整 **retrieval-augmented generation**：

1. 讀入獨立的 `data/knowledge.json`，每筆餐點為一個文件片段。
2. 正規化料理／食材別名與常見中英用詞、比薩／披薩等變體，再以中文單字與雙字、英文詞組建立稀疏 TF-IDF 向量（單字特徵權重 0.3，雙字／英文詞組權重 1）。
3. 先套用國家／地區、主食、主要食材、排除食材與半徑條件。
4. 分離分類條件與額外餐點關鍵字。餐點關鍵字須逐筆通過覆蓋率 60%、原始餘弦相似度 0.04 的起始門檻，再用距離乘數調整排序，餐廳去重。
5. 將排序前 3 家餐廳的實際檢索片段與條件送入 Qwen2.5 1.5B。模型根據問題與片段推薦首選，解釋備選適合的情境，並附參考來源。

AI 使用 [WebLLM](https://github.com/mlc-ai/web-llm) `0.2.88` 與 `Qwen2.5-1.5B-Instruct-q4f32_1-MLC`，透過專用 Worker 在瀏覽器本機推論。需 WebGPU、足夠 GPU 記憶體，首次約 1 GB 下載（實際以引擎下載量為準）。模型與引擎需外部連線，模型檔由 Hugging Face 提供；沒有 WebGPU 或載入失敗會保留摘要功能。模型生成文字仍可能出錯，卡片與檢索依據可核對原始資料。

### 推薦分數

`distanceScore = 1 / (1 + straightLineMeters / 500)`

`relevance = 0.65 * keywordCoverage + 0.35 * rawCosineSimilarity`

`score = relevance * ((1 - weight) + weight * distanceScore)`

關鍵字覆蓋率為「候選文件中命中的查詢特徵 IDF 權重合計／全部查詢特徵 IDF 權重合計」，單字特徵使用 0.3 倍權重。使用**額外餐點關鍵字**計算，不讓共同的「韓國、飯」等分類掩蓋「鰻魚」缺少證據的問題；未知特徵仍計入分母。覆蓋率不足 60% 或原始相似度低於 0.04 的候選直接排除，不會依候選最高分放大至 1，也不再給文字零命中的餐點 0.55 保底。

只指定分類／食材而沒有額外菜名（例如「韓式、有飯、不吃牛」）時，以**條件篩選**顯示，條件符合值為 1，再用距離調整順序；沒有問句的探索頁也是此類瀏覽。介面不會把這些結果誤標為文字相似度命中。

距離權重預設由 35% 調為 **25%**，可調 0–80%。乘數不超過 1，文字相關度為零就不會因距離產生正分；「距離最近」排序同樣只能重排已通過門檻的資料。權重與門檻是起始設定，經已收錄菜名與正反例檢查，並非以真實使用者偏好調出的最佳比例。符合分數不是品質評分或正確率。資料未收錄時應針對缺口補查有來源的品項，單純擴充數量無法取代檢索門檻。

距離以 Haversine 計算約略座標間直線距離，**不是步行距離或步行時間**。京站店家共用建物座標，示意圖為可讀性稍微分散同址標記。實際路線由 Google Maps 導航。

## 本機執行與驗證

在專案根目錄啟動任意靜態 HTTP 伺服器，例如 `python -m http.server 8765`，開啟 `http://localhost:8765/food-rag/`。不可直接雙擊 HTML，因模組與 JSON fetch 需要 HTTP。

推薦引擎測試：開啟 `http://localhost:8765/food-rag/tests/`，所有斷言結果會在頁面列出。測試頁不會複製到正式 Pages。

## GitHub Pages

沿用上層專案 `.github/workflows/pages.yml`。推送 `main`／`master` 會部署。Workflow 僅白名單複製網站資產與知識庫，避免發布工作目錄的 `.env`、本機憑證及其他未追蹤檔。部署網址以 GitHub 回傳為準，預期新頁路徑為 `https://lucas950219.github.io/-/food-rag/`。

## 更新資料

編輯 `data/knowledge.json` 的 `restaurants`、`foods`、`sources`，每個餐點保留來源 ID；更新查閱日與 `data/SOURCES.md`，再執行測試。`branch-menu` 表示分店公開資料，`brand-menu` 表示品牌參考品項、分店供應待確認。主要食材未知不能作為不含牛豬的保證；排除食材時會排除主要食材未知的餐點，但湯底、醬汁與交叉接觸仍須向店家確認。未收錄即時價格、營業時間、庫存、評價、訂位或飲食認證。

收藏只保存在瀏覽器 localStorage，無帳號、後端、分析追蹤與提問紀錄上傳。字型由 Google Fonts 載入，無連線時使用系統字型。
